# Next direction: matrix-free local inversion, prototype stage only

Development20's48cells completed and both powered objectives worsened quality. The objective audit still shows a large gap between the wrong reconstructed states and the correct baseline states, and development19 did not fix it by changing readout. The next hypothesis is that a better inverse direction can cross this gap with fewer nonlinear evaluations than logit optimization.

The implemented core in scripts/trr0020_stage21 contains an unpadded Llama-style causal forward, analytic own-position Jacobian-vector products, and a batched regularized Krylov least-squares solver. RMS normalization, rotary Q/K, grouped-query attention, the current query/key/value paths, SwiGLU and residual connections are included. Other positions' K/V derivatives are excluded deliberately: this is the block diagonal of the causal sequence Jacobian, not the full Jacobian. There is no model fitting, learned inverse, shortlist, candidate pruning or candidate verification in this core.

The intended future reconstruction would solve each position's local raw-activation equation in parallel, update continuous embeddings, refresh the forward cache, and ultimately read the complete vocabulary directly. A short unchanged Gini warm start is a possible initializer. None of those full reconstruction decisions is implemented or registered yet; no GPU grid, accuracy or speed claim is implied by this prototype.

The derivative calculation reuses stored forward intermediates and frozen matrices. It does not construct a dense2048x2048Jacobian for each position. The linear routine builds a small Arnoldi basis with two-pass modified Gram-Schmidt and solves a ridge-regularized normal equation. The ridge makes this an approximate regularized Krylov solve, not an exact unregularized GMRES guarantee. It must report true linear residuals and all matrix-vector costs.

CPU qualification uses seed200048, float64, two causal layers, four positions, width8and grouped-query attention. Compare five analytic products to independent dense autograd Jacobian blocks; verify zero derivatives from future inputs; compare the eight-step linear direction with torch.linalg.solve; and exercise a zero right-hand side. Record source hashes, full code commit, exact command, runtime and package versions. This proves tiny algebra only.

Before GPU reconstruction, separately qualify the FP32forward against an independent supplied-prefix implementation, check actual own-position products against autograd directional derivatives on public inputs at40and128positions, and qualify the linear solve and largest cache geometry with a live resource preflight. FP32forward arithmetic is a new numerical method, not a claimed equivalent execution of native BF16A2. The existing prefix metric/initialization cannot be silently changed. No autograd dense2048x2048-per-position construction is authorized without a separate resource estimate.

Estimate tensor geometry and runtime before allocating real-prefix FP32copies or releasing a matrix. Keep all observed-model costs, initialization, FP32weight preparation, cache construction, matrix-vector products and full-vocabulary readout in the evidence. Preserve numerical/resource failures. A prospective finite grid and complete freeze gate remain required before hidden-label scoring; any selected rule must then complete both canonical setups and the full active matrix.
